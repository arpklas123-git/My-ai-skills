# wtf

에러를 받으면 **원인 → 재현 → 고칠 자리** 순서로 답한다. 코드는 사용자가 고쳐달라고 하기 전까지 건드리지 않는다.

## 1. 진짜 프레임을 찾는다

스택트레이스는 위에서부터 읽지 말고, **내 코드가 마지막으로 나오는 프레임**을 찾는다. 라이브러리 내부에서 터졌어도 원인은 거기 넘긴 값에 있는 경우가 대부분이다.

- 에러 타입과 메시지를 분리해서 본다. `NoneType has no attribute` 는 "None이 어디서 왔나"가 질문이지 그 줄이 문제가 아니다.
- `Caused by` / `during handling of the above` 가 있으면 **가장 안쪽**이 진짜다.
- 로그가 길면 첫 에러만 본다. 뒤따르는 건 대개 파생이다.

## 2. 코드를 실제로 읽는다

추측 금지. 트레이스에 나온 파일을 열어서 해당 줄과 그 값이 만들어진 곳까지 거슬러 올라간다. 최근에 바뀐 코드가 범인일 확률이 높으니 `git log -p -3 <file>` 이나 `git diff` 를 확인한다.

환경 문제가 의심되면 (버전 불일치, 없는 env var, 경로, 권한) 추측 대신 확인하는 명령을 실제로 돌린다.

## 3. 이렇게 답한다

```
원인: <한 문장. 무엇이 무엇을 기대했는데 실제로 뭐가 왔는지>

왜 그런가:
  <2-4줄. 값이 어디서 출발해서 어디서 어긋났는지 경로>

고칠 자리:
  path/to/file.py:123  <무엇을 어떻게>

확인:
  <이게 원인인지 검증하는 명령 한 줄>
```

## 규칙

- **모르면 모른다고 한다.** 후보가 둘이면 둘 다 쓰고, 어느 쪽인지 가르는 확인 방법을 준다. 확신 없는 걸 확신하는 척하면 이 스킬은 쓸모가 없다.
- 증상만 덮는 수정(빈 try/except, 널 체크 하나 추가)은 그게 정답일 때만 제안한다. 아니면 그렇게 말한다.
- 재현이 안 되는 문제(간헐적, 특정 환경)면 그 사실을 먼저 말하고, 다음에 터졌을 때 뭘 남겨야 하는지 알려준다.
- 답은 짧게. 에러 하나에 문단 다섯 개는 필요 없다.
